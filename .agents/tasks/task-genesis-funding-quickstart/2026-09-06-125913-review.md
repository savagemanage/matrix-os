# Re-review of v1 fixes: fund auth gate, wallet pairing, watcher/inference docs (v2)

Fix commit `86c7d39` addresses the five findings from the v1 review (`2026-09-06-124319-review.md`), which returned NEEDS_CHANGES. This pass verifies each fix against the code and its tests and checks for regressions. The most consequential fix is the reward-pool drain: `FundAccount` now refuses to run unless the hosting server enforces authentication, recorded from `cfg.Auth != nil` in `NewServer`, so an ACLs-off node returns `FailedPrecondition` instead of moving reward-pool MATRIX for an unauthenticated caller. The other four fixes correct documentation to match reality (bridge watcher cursor, `cmd/bridge-watch` integration claim), add derive-and-compare key-pairing checks to both wallet loaders, and rebuild the inference web one-liner into a fund → register → submit sequence with an ACL/`--api-key` note.

Watch for: nothing blocking. All five findings are resolved; the fund-auth gate is behaviorally sound and backed by a regression test that fails if the gate is removed (confirmed), and the legitimate funding path still works end to end with a valid key (confirmed).

**Verdict**: APPROVED

## High-level view

The unauthenticated-drain hole is closed at the right layer. `Service` carries an `authEnforced` flag set once during `NewServer` from `cfg.Auth != nil`, and `FundAccount` short-circuits to `FailedPrecondition` before touching the funder when the flag is false. Because `FundAccount` alone among mutating RPCs carries no per-request signature, this restores the "every mutating RPC is authorized" invariant the market-auth note in `node.go` relies on. The node wires `Auth` only when `Security.EnableACLs` is set, so an open node has `authEnforced == false` and cannot fund.

The two documentation findings are now honest. The dead `watcherCursorKey` constant is gone and the watcher comments state plainly that no cursor is persisted, restart re-scans from `StartBlock`, and the re-scan is harmless because `ProcessBurn` dedups by burn id. The `cmd/bridge-watch` header no longer claims an in-matrixd watcher deployment "this command's Watcher is built to support"; it says matrixd does not construct a Watcher and that in-node wiring is a remaining item.

Both wallet loaders now verify the stored public key is the one the private key derives. The CLI `loadWallet` returns a hard error on mismatch; the inference on-disk resolver `loadWalletAccount` returns `(nil, false)` so a corrupt file is skipped rather than surfaced as a resolvable account — the right asymmetry for a resolver that must never hand back an account whose signature would not verify against its id.

The inference web command is now runnable-accurate: it resolves `BUYER`, funds it, registers `demo-inference-provider` with capacity and price, then submits, and every flag matches the shipped CLI (`fund --account/--amount`, `provider register --id/--capacity/--price`, `inference submit --buyer/--provider/--prompt`). The surrounding prose adds the `--api-key` requirement under default ACLs and notes an open node will not expose funding at all.

### Finding 3 — FundAccount unauthenticated drain (resolved, confirmed)

The gate lives in the handler ahead of argument validation and the funder call:

```go
if s.funder == nil { return Unimplemented }
if !s.authEnforced {
    return FailedPrecondition,
        "reward-pool funding requires authentication: enable ACLs ... to expose FundAccount"
}
```

`authEnforced` is set exactly once by `NewServer` via `svc.SetAuthEnforced(cfg.Auth != nil)` before serving. The node constructs the market server only through `NewServer` (the sole `marketapi.NewServer` call outside tests is in `node.go`, and it passes `Auth: marketAuth`, which is non-nil only inside the `if n.config.Security.EnableACLs` branch), so an ACLs-off node has `authEnforced == false` and `FundAccount` refuses before moving anything.

The two failure paths are distinct and both covered. On an auth-off server the handler-level gate returns `FailedPrecondition` (no interceptor runs at all — this is the hole the gate closes). On an auth-on server a call with no credentials is rejected by the interceptor with `Unauthenticated` before reaching the handler. `TestFundAccount_RejectedWithoutAuth` builds the harness with `withAuth=false` and asserts `FailedPrecondition` plus zero movement (attacker balance 0, pool unchanged) — removing the gate would let the call reach the funder and this test would fail. `TestFundAccount_RejectedWithoutCredentials` asserts `Unauthenticated` on the auth-on server with no key. The legitimate path is preserved: the default `newFundHarness` now enables auth and the positive tests (`MovesRewardPoolFunds`, `RejectsOverPool`, `ValidatesArgs`) call through `authCtx`, and the CLI `fund`/`quickstart` harnesses enable ACLs and pass `--api-key`, exercising the real funding flow end to end.

### Findings 1 & 2 — bridge watcher cursor and bridge-watch integration claim (resolved, confirmed)

`watcherCursorKey` is deleted; the only surviving reference to "persisted cursor" is the new comment explaining one is deliberately *not* wired. The `WatcherConfig.StartBlock` doc and the `Poll` cursor-advance comment now describe an in-memory-only cursor that resets to `StartBlock` on a fresh process, with the harmless-re-scan rationale tied to `ProcessBurn`'s per-burn-id replay guard. The `cmd/bridge-watch` header now states matrixd does not construct or run a Watcher and points at `STILL-REMAINING.md` for the in-node wiring as a future item. No code claims a persistence or in-matrixd mechanism that does not exist.

### Finding 5 — wallet key pairing (resolved, confirmed)

Both loaders derive `priv.Public()` and compare against the stored public key. `internal/cli/wallet.go` fails with a clear "wallet is corrupt: its private key does not match its public key" error; `internal/node/inference_accounts.go` returns `(nil, false)` so the resolver skips the file. `TestWalletAccounts_RejectsMismatchedKeyPair` splices account A's private key with account B's public key and asserts the resolver rejects it. The asymmetry (hard error in the CLI, silent skip in the resolver) is correct: a resolver iterating candidate wallet files should not abort the whole resolution because one file is corrupt, but must never surface an account whose signing key would produce a signature failing verification against its id.

### Finding 4 — inference web command prerequisites (resolved, confirmed)

`INFERENCE_CLI_COMMAND` is now a four-line block: resolve `BUYER` from `matrix wallet show`, `matrix fund --account "$BUYER" --amount 1000000`, `matrix provider register --id demo-inference-provider --capacity 1000 --price 5`, then `matrix inference submit --buyer "$BUYER" --provider demo-inference-provider --prompt "hello world"`. Every flag matches the shipped CLI definitions. The added prose states the buyer must be funded and the provider registered before a job can reserve and settle, that a default node runs with ACLs enabled so each command needs `--api-key <key>`, and that an open dev node will not expose reward-pool funding — which is exactly consistent with the finding-3 gate.
