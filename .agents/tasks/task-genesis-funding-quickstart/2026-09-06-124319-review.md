# Native genesis funding, one-command quickstart, inference + bridge wiring (v1)

Wires four previously-standalone subsystems into a bootable node and its CLI/web surfaces: the native MATRIX treasury (genesis + reward pool) is now constructed and applied on `Start`; a `FundAccount` market RPC and `matrix fund` move reward-pool MATRIX into accounts without minting; a `matrix quickstart` runs the whole zero-to-first-job loop; the inference service is served on its own gRPC port with a wallet-backed key-custody resolver and a `matrix inference` CLI; and a standalone burn→unlock bridge watcher (`cmd/bridge-watch`) polls an Ethereum endpoint through the replay-safe `ProcessBurn`. README and the web product pages are updated to the native-first story with click-to-copy commands. The money-movement paths (genesis, funding, settlement) are cap-enforced and conserve supply, and the honest custody/automation boundaries are mostly stated accurately.

Watch for: (1) the bridge Watcher documents a persisted cursor and "resumes without re-scanning," but no store is ever wired in and the `watcherCursorKey` constant is dead — on restart it re-scans from `StartBlock` (confirmed); (2) `cmd/bridge-watch` claims the watcher runs "inside matrixd against the node's own ledger," but no watcher is wired into `node.go` (confirmed); (3) `FundAccount` is gated only by the ACL flag and, unlike `SubmitSignedTransfer`, requires no signature, so an ACL-disabled node lets any client drain the reward pool into any account (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The treasury is constructed right after the market ledger and token chain, and genesis is applied unconditionally on every `Start`, before any funding or settlement can run. Idempotency and the supply cap live in the pre-existing `token.Treasury`. The default `matrixd --init` seeds `reward_pool = NativeMaxSupply` with no named allocations, so total genesis issuance sits exactly at the cap.

Funding moves coins out of the reward pool via a narrow consumer-side `Funder` interface satisfied by `*token.Treasury`; it never mints, and cap/insufficient-pool errors map to `FailedPrecondition`. The one posture gap is authentication: `FundAccount` inherits the same ACL gate as every other RPC but, unlike the signed-transfer path, carries no per-request signature, so on an open node it is an unauthenticated reward-pool drain into an attacker-named account (bounded by the pool balance and the cap, but free money nonetheless).

The p2p `listen_addr` change is a genuine fix, not a risk: the old code rejected the `host:port` form the default config actually uses (it fed `0.0.0.0:9000` into an `/ip4/.../tcp/0` template and errored), so a freshly-initialized node could not boot from its own default. The new `listenMultiaddr` accepts multiaddr, `host:port`, bare `:port`, IPv6, and hostnames, and preserves the configured port. Multiaddr and empty-string configs behave identically to before.

Inference is served on its own gRPC port and settles buyer→provider through the same consensus engine as compute, so there is one ledger. Custody is honest: the node signs only for buyers whose keys it legitimately holds, resolved from in-memory registrations or on-disk wallets under `~/.matrix`; it never fabricates keys. The wallet loader does not check that a wallet file's private key actually matches its public key, but a forged pairing simply fails signature verification downstream, so it is not a theft vector on this single-operator model.

The bridge watcher correctly relies on `ProcessBurn`'s per-burn-id replay guard, so re-observing a burn is a benign no-op and restart safety is preserved for correctness. What is overstated is durability and integration: the cursor is never persisted (the `watcherCursorKey` constant and its doc comment describe a store that no config field exposes), and `cmd/bridge-watch`'s comment claims an in-matrixd deployment that does not exist in this change. The relayer-not-consensus automation boundary itself is stated accurately.

README and web copy are accurate to what ships: every referenced screenshot exists, the native/wMATRIX distinction is correct, and the copy-to-clipboard commands map to real CLI subcommands. The inference-page one-liner depends on `matrix wallet show` output and is parsed correctly, but it shows only the submit step, omitting the fund + provider-registration prerequisites the job actually needs.

### Genesis applied in-order, at the cap

Genesis is applied unconditionally on every `Start`, before the P2P host, market API, and inference API come up, so no settlement or funding can observe a pre-genesis ledger. The `alreadyApplied` read taken before `ApplyGenesis` only drives the log line; idempotency is enforced inside `Treasury.ApplyGenesis` under the ledger lock, so the extra read opens no TOCTOU window.

The `matrixd --init` default seeds `reward_pool = token.NativeMaxSupply` with no named allocations. That places total genesis issuance exactly at `NativeMaxSupply`, which `ApplyGenesis` permits (the cap check is `total > NativeMaxSupply - x`, i.e. `<=` is allowed), so a default node comes up with the entire supply parked in the reward pool and nothing mintable beyond it.

### Reward-pool funding conserves supply but skips signatures

```
FundAccount RPC ──► Funder.FundFromRewardPool ──► ledger.Atomically(Transfer reward-pool ─► recipient)
```

`FundAccount` moves existing coins out of `native/reward-pool`; it never calls a minting primitive, so issued supply is unchanged and the cap holds by construction. Insufficient-pool and `ErrSupplyCapExceeded` both map to `FailedPrecondition`, and a node built without a treasury returns `Unimplemented` rather than pretending to fund.

The gap is authorization. The comment on the market auth wiring argues an open (ACLs-off) node is safe because `SubmitSignedTransfer` still requires a valid ed25519 signature and correct nonce, so a caller can only move credits it holds the key for. `FundAccount` breaks that argument: it takes only an account id and amount, no signature, so with ACLs disabled any client on the wire can transfer reward-pool MATRIX to any account id it chooses. The damage is bounded — no minting, capped by the pool balance — but it is still an unauthenticated value movement that the surrounding security note implicitly claims does not exist on this surface. Either require an authorized/signed funding request or make the open-node posture note explicit that reward-pool funding must not be exposed without ACLs.

### p2p listen_addr: a real boot fix, not a regression

The previous `New` tried `multiaddr.NewMultiaddr(cfg.ListenAddr)` and, on failure, `multiaddr.NewMultiaddr(fmt.Sprintf("/ip4/%s/tcp/0", cfg.ListenAddr))`. For the `0.0.0.0:9000` form the config actually wrote, both fail (`/ip4/0.0.0.0:9000/tcp/0` is not a valid multiaddr), so a freshly-initialized node could not boot from its own default listen address. `listenMultiaddr` replaces this with explicit handling: empty → all-interfaces random port, leading `/` → verbatim multiaddr, otherwise `net.SplitHostPort` + protocol detection (`ip4`/`ip6`/`dns`) rebuilding a proper `/…/tcp/<port>` and preserving the configured port. Multiaddr and empty-string inputs behave exactly as before; the only behavioral change is that `host:port` now works instead of erroring. The host_test table covers multiaddr passthrough, IPv4/IPv6 host:port, bare `:port`, hostname→dns, and bad-port rejection, plus an actual libp2p boot on a loopback host:port.

### Inference custody: honest, but key pairing unchecked

Settlement requires the buyer's signing key, and rather than assume custody the service is handed a `walletAccounts` resolver that resolves ids from in-memory registrations first, then wallet files under `~/.matrix` whose public key equals the requested id. It only ever surfaces keys that already exist as a registration or an on-disk wallet, so it cannot fabricate custody — the correct single-operator/dev model, with multi-tenant deployments expected to substitute their own custodial resolver.

`loadWalletAccount` reconstructs the account from the hex pub/priv halves but never checks that the private key actually derives the stored public key. Because the account id is the public key and the downstream consensus transfer is verified against that public key, a mismatched file just produces a signature that fails verification — not a way to spend someone else's balance. Still, a `ed25519.PrivateKey.Public()`-and-compare on load would fail fast on a corrupt or hand-edited wallet instead of at settlement time.

### Bridge watcher: replay-safe, but durability and integration are overstated

The Watcher polls `eth_getLogs` for `Burned` events from `StartBlock`, decodes each, and drives it through `ProcessBurn`, which is replay-protected per burn id (a re-observed burn returns `ErrBurnAlreadyProcessed`, which `applyLog` treats as a benign zero-applied no-op). Transient RPC errors and single malformed logs are reported via `OnError` and retried on the next tick rather than wedging the loop, and the confirmations offset (`head - confirmations`) lets an operator stay behind head to avoid acting on a reorged burn.

Two documentation claims are not backed by code. First, the `watcherCursorKey` constant and its comment ("stored under the bridge/* namespace so a restarted watcher resumes without re-scanning… a persisted cursor (when Store is set) takes precedence on resume") describe a persistence mechanism that does not exist: `WatcherConfig` has no `Store` field, the Watcher never reads or writes the cursor, and the constant is referenced only in comments. On restart the watcher resumes from `StartBlock` and re-scans (harmlessly, thanks to dedup) — the opposite of "without re-scanning." Second, `cmd/bridge-watch`'s header says a production deployment can run "the watcher inside matrixd against the node's own ledger, which this command's internal/bridge.Watcher is built to support," but no Watcher is constructed anywhere in `node.go`; the only runtime is this throwaway single-pass relay over a temp ledger. The relayer-not-consensus automation boundary ("it does not itself reach multi-validator consensus on the unlock") is stated accurately and is the right caveat; only the persistence and in-matrixd claims need correcting.

### README and web copy match what ships

All ten screenshots referenced by README exist under `docs/screenshots`, and the native-vs-wMATRIX framing (native MATRIX as the L1 source of truth, wMATRIX as the bridged ERC-20 mirror, cap 1,000,000,000 at 9 decimals) is consistent with the treasury code. The home and CLI copy-to-clipboard payloads strip `$ ` prompts and map to real subcommands (`quickstart`, `fund`, `provider register`, `job submit`, `wallet transfer`, all registered in `root.go`). The inference-page one-liner parses `matrix wallet show` with `awk '/^account:/{print $2}'`; despite the multi-space padding in `account:    <id>`, awk's default field splitting picks the id correctly. The one accuracy gap is completeness: that command shows only `inference submit`, but the job needs the buyer funded and the provider registered and reserved first, so pasted verbatim against a fresh node it will fail on capacity/affordability unless the surrounding page prose supplies those steps.
