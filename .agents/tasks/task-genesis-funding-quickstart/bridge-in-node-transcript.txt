Live proof: the burn->unlock watcher running INSIDE matrixd, against a local
hardhat chain, unlocking on the node's own ledger.

What this adds over the Go tests: the tests drive the wiring with a fake
EthClient. This run boots the real matrixd binary from a config file, dials a
real Ethereum JSON-RPC endpoint, decodes a real on-chain Burned event, and
credits the node's real market ledger, verified through the market gRPC API.

CAVEAT, stated plainly: escrow is seeded by a genesis allocation to
bridge/escrow, standing in for prior locks. A genesis credit does not increment
the bridge's locked-total counter, so Bridge.Reconcile is deliberately NOT asserted
in this run. The full lock -> burn -> unlock -> Reconcile path (with a real
Bridge.Lock first) is covered by the Go test
internal/node.TestNodeBridgeWiring_BurnUnlocksOnTheNodeLedger.

(WrappedMatrix deployed, wMATRIX minted from a REAL Go-produced attestation,

Escrow went 8000000000 -> 7999999997: the 3 native base units were RELEASED FROM
THE NODE'S OWN ESCROW to the burn's named recipient. cmd/bridge-watch cannot
show this -- it applies burns to a throwaway ledger of its own.

-------------------------------------------------------------------------------
5. Boot 2 (restart): the persisted cursor resumes instead of re-scanning
-------------------------------------------------------------------------------
$ # graceful shutdown, then start the same config again
$ ./matrixd --config ./config.yaml
Genesis already applied; skipping (idempotent).
Inference: registered echo backend for demo provider "demo-inference-provider".
Bridge: enabled for WrappedMatrix 0x5fbdb2315678afecb367f032d93f642f64180aa3 on chain 31337.
Bridge watcher: polling http://127.0.0.1:8545 from block 4 (0 confirmations).

"polling ... from block 4" -- NOT from block 0 (start_block). The cursor
persisted in the node's KV store, so the already-scanned range [0,3] is skipped,
and boot 2 logs no unlock at all: there is nothing left to re-observe.

Confirmed against the chain's own request log: at this point eth_getLogs had
been called exactly ONCE across both boots -- boot 1's scan of [0,3]. Boot 2
issued none, because its cursor (4) was already past head (3), so its polls had
no final range to request. (After the new burn in section 6 the count rises to
two, which is that burn being scanned.)

Balances unchanged after the restart -- no double unlock:
  beef...beef : 3
  bridge/escrow: 7999999997

-------------------------------------------------------------------------------
Summary of what this run proves
-------------------------------------------------------------------------------
- matrixd boots the bridge subsystem from config and validates it at startup.
- The in-node watcher dials a real Ethereum endpoint and decodes a real
  on-chain Burned event.
- The unlock is applied to the node's OWN market ledger, released from the
  node's OWN escrow, and is readable over the node's market API.
- The scan cursor persists across a matrixd restart: the watcher resumes at the
  next unscanned block, issues no redundant eth_getLogs, and does not double
  unlock.
- A watcher resumed from a persisted cursor keeps relaying new burns.

What this run does NOT prove (unchanged boundaries):
- Multi-validator consensus on the unlock. The watcher is a per-node relayer;
  running it inside matrixd does not make the unlock consensus-ordered.
- Reconcile against real locks (see the CAVEAT at the top; covered by the Go
  test instead).
- Anything against a real testnet/mainnet deployment, which needs the
  operator's funded key.
